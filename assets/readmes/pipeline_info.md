# pipeline_info — Nextflow Execution Reports

This directory contains reports generated automatically by [Nextflow](https://www.nextflow.io/) and the pipeline itself to document the execution of the run.

## Files

| File | Description |
|------|-------------|
| `execution_report.html` | Interactive HTML report with per-process resource usage, timeline, and task status |
| `execution_timeline.html` | Gantt-chart view of task start/end times — useful for identifying bottlenecks |
| `execution_trace.txt` | Tab-delimited table of every task with CPU, memory, wall-clock time, and exit status |
| `pipeline_dag.dot` / `pipeline_dag.svg` | Directed-acyclic graph (DAG) of the pipeline workflow |
| `params.json` | Complete record of all parameters used in this pipeline run |
| `software_versions.yml` | Versions of every software tool used in the run |
| `samplesheet.valid.csv` | The validated samplesheet that was actually used as pipeline input |
| `pipeline_report.html` / `pipeline_report.txt` | Pipeline-level summary report (only generated when `--email` or `--email_on_fail` are set) |

## How These Files Are Derived

All files in this directory are generated automatically by Nextflow or the nf-core pipeline framework:

- **Execution report / timeline / trace** — Nextflow instruments each task and writes these files when the workflow completes. They record the actual resources consumed (vs. the requested resources) and can guide future resource tuning.
- **DAG** — Nextflow renders the workflow process graph using Graphviz (`.dot`) or SVG. A PNG/HTML version can be generated by passing `-with-dag flowchart.html` when launching the pipeline.
- **`params.json`** — All `params.*` values from `nextflow.config`, the command line, and any `--params-file` are written here, providing a full reproducibility record.
- **`software_versions.yml`** — Each module emits a `versions.yml` file; the pipeline collects and deduplicates these into a single file. MultiQC also renders this in its report.

## Troubleshooting Failed Runs

1. Open `execution_report.html` → filter for tasks with status `FAILED`.
2. Click on the failed task to see its working directory path.
3. Navigate to that working directory under `work/` and inspect `.command.log` and `.command.err` for the actual error message.
4. `execution_trace.txt` provides the exit code and peak memory/CPU usage for every task.

## Reproducing This Run

To reproduce this run exactly, supply the same parameters from `params.json` and pin tool versions using the container image recorded in `software_versions.yml` or the pipeline release tag.
